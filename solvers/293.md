# Project Euler 293 Solution - Pseudo-Fortunate Numbers

<https://projecteuler.net/problem=293>:

* [293.py](293.py)

## Problem Summary

An [even integer](https://ourbigbook.com/codex/even-integer) $n$ is called admissible when it is either a power of $2$ or, equivalently for [even numbers](https://ourbigbook.com/codex/even-number), its distinct [prime factors](https://ourbigbook.com/codex/prime-factor) form a consecutive prefix of the [prime](https://ourbigbook.com/codex/prime) list $2,3,5,7,\ldots$. For every admissible $n < 10^9$, define $M(n)$ as the smallest [integer](https://ourbigbook.com/codex/integer) $m>1$ such that $n+m$ is [prime](https://ourbigbook.com/codex/prime). The task is to sum the distinct values of $M(n)$.

## Mathematical Approach

### 1. Exact shape of admissible numbers

Because $n$ is even, the first [prime](https://ourbigbook.com/codex/prime) $2$ must appear. If the distinct [prime factors](https://ourbigbook.com/codex/prime-factor) are consecutive, then every admissible number has the form

$$n = 2^{a_1} 3^{a_2} 5^{a_3} \cdots p_k^{a_k}, \qquad a_i \ge 1.$$

The special case "power of $2$" is simply the case $k=1$. So admissible numbers are described completely by choosing a [prime](https://ourbigbook.com/codex/prime) prefix and choosing a positive [exponent](https://ourbigbook.com/codex/exponent) for each [prime](https://ourbigbook.com/codex/prime) in that prefix.

This already gives a strong bound on the search space. The product of the first nine [primes](https://ourbigbook.com/codex/prime) is

$$2\cdot 3\cdot 5\cdot 7\cdot 11\cdot 13\cdot 17\cdot 19\cdot 23 = 223092870 < 10^9,$$

while including the next [prime](https://ourbigbook.com/codex/prime) gives

$$223092870 \cdot 29 = 6469693230 > 10^9.$$

Therefore no admissible number below $10^9$ can contain $29$ or any later [prime](https://ourbigbook.com/codex/prime) as a distinct factor. The code keeps a slightly longer fixed [prime](https://ourbigbook.com/codex/prime) list, but [recursion](https://ourbigbook.com/codex/recursion) automatically prunes everything beyond the limit.

### 2. Why the DFS generation is exact

The recursive generator works on the ordered [prime](https://ourbigbook.com/codex/prime) list $(2,3,5,7,\ldots)$. Suppose we are currently at [prime](https://ourbigbook.com/codex/prime) $p_i$ with a partial product built from the earlier prefix. The loop repeatedly multiplies by $p_i$:

$$\text{current},\ \text{current}\cdot p_i,\ \text{current}\cdot p_i^2,\ \text{current}\cdot p_i^3,\ldots$$

as long as the product stays below the limit. Every time at least one copy of $p_i$ has been chosen, the [recursion](https://ourbigbook.com/codex/recursion) may continue to the next [prime](https://ourbigbook.com/codex/prime) $p_{i+1}$.

This does exactly what we need:

**Positive [exponents](https://ourbigbook.com/codex/exponent).** Once a [prime](https://ourbigbook.com/codex/prime) is included, it appears with [exponent](https://ourbigbook.com/codex/exponent) at least $1$.

**Consecutive prefix only.** The [recursion](https://ourbigbook.com/codex/recursion) may move from $p_i$ to $p_{i+1}$ only after choosing $p_i$, so later [primes](https://ourbigbook.com/codex/prime) can never appear while skipping an earlier one.

**No duplicates.** Each [exponent vector](https://ourbigbook.com/codex/exponent-vector) $(a_1,\ldots,a_k)$ corresponds to one unique [recursion](https://ourbigbook.com/codex/recursion) path.

So the [DFS](https://ourbigbook.com/codex/depth-first-search) enumerates every admissible number once and only once, without scanning all [even integers](https://ourbigbook.com/codex/even-integer) up to $10^9$.

### 3. Why the pseudo-Fortunate search starts at $3$

By definition, $M(n)$ is the smallest [integer](https://ourbigbook.com/codex/integer) $m>1$ such that $n+m$ is [prime](https://ourbigbook.com/codex/prime). Since every admissible $n$ is even, any [prime](https://ourbigbook.com/codex/prime) larger than $2$ has to be odd, so $m$ must be odd as well. Therefore the candidates are exactly

$$m = 3,5,7,9,\ldots$$

and the code tests them in increasing order until $n+m$ is [prime](https://ourbigbook.com/codex/prime).

For example, $16$ is admissible because it is a power of $2$. We cannot use $m=1$ because the definition requires $m>1$. Then

$$16+3 = 19,$$

which is [prime](https://ourbigbook.com/codex/prime), so

$$M(16)=3.$$

Likewise, $630 = 2\cdot 3^2\cdot 5\cdot 7$ is admissible because its distinct [primes](https://ourbigbook.com/codex/prime) are $2,3,5,7$. Testing odd values gives

$$630+3=633,\ 630+5=635,\ 630+7=637,\ 630+9=639,$$

all [composite](https://ourbigbook.com/codex/composite-number), while

$$630+11=641$$

is [prime](https://ourbigbook.com/codex/prime), hence

$$M(630)=11.$$

### 4. Why we need a set of pseudo-Fortunate values

The problem asks for the sum of *distinct* values $M(n)$, not the sum over all admissible $n$. Different admissible numbers can share the same pseudo-Fortunate value, so the implementation inserts each result into a [set](https://ourbigbook.com/codex/set) first:

$$\mathcal{M} = \{M(n) : n \text{ admissible},\ n < 10^9\}.$$

The final answer is then

$$\sum_{m \in \mathcal{M}} m.$$

This is mathematically important: without deduplication we would answer a different question.

### 5. Primality testing is the main inner operation

After admissible numbers have been generated, the expensive repeated task is to test whether $n+m$ is [prime](https://ourbigbook.com/codex/prime). The code uses deterministic Miller-Rabin for 64-bit [integers](https://ourbigbook.com/codex/integer), so each test is exact in this range and still very fast. That makes the straightforward odd-step search practical.

### 6. Checkpoints and interpretation

The implementation verifies itself with three simple checks:

$$M(16)=3,\qquad M(630)=11,\qquad \text{solve}(10000)=\text{solve\_bruteforce}(10000).$$

The first two confirm the pseudo-Fortunate search itself. The third compares the efficient [DFS](https://ourbigbook.com/codex/depth-first-search) enumeration against a [brute-force](https://ourbigbook.com/codex/brute-force-search) admissibility test on a smaller limit, which is a strong check that the generator is complete and duplicate-free.

## How the Code Works

`prime_prefix()` provides a fixed [initial segment](https://ourbigbook.com/codex/initial-segment) of the [prime](https://ourbigbook.com/codex/prime) list. `generate_admissible(...)` performs the [DFS](https://ourbigbook.com/codex/depth-first-search) over [exponent](https://ourbigbook.com/codex/exponent) choices and stores every admissible product in a [set](https://ourbigbook.com/codex/set). For each stored $n$, `pseudo_fortunate(n)` checks odd $m=3,5,7,\ldots$ until $n+m$ is [prime](https://ourbigbook.com/codex/prime). These $M(n)$ values are inserted into another [set](https://ourbigbook.com/codex/set), and the program sums that [set](https://ourbigbook.com/codex/set) at the end.

## Complexity Analysis

Let $A$ be the number of admissible numbers below the limit, and let $T(n)$ be the number of odd candidates tested before finding $M(n)$. Then the total running time is roughly

$$O\!\left(A + \sum_{n \in \text{admissible}} T(n)\cdot C_{\text{prime}}\right),$$

where $C_{\text{prime}}$ is the cost of one [primality test](https://ourbigbook.com/codex/primality-test). Memory usage is $O(A + |\mathcal{M}|)$ for the two [sets](https://ourbigbook.com/codex/set). The crucial gain comes from generating only admissible numbers rather than scanning all [even numbers](https://ourbigbook.com/codex/even-number) up to $10^9$.
