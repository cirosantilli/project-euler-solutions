# Project Euler 289 Solution - Eulerian Cycles

<https://projecteuler.net/problem=289>:

* [289.py](289.py)

This repo contains a Python solution for **Project Euler Problem 289**.

We count [Eulerian cycles](https://ourbigbook.com/codex/eulerian-cycle) on the [circle](https://ourbigbook.com/codex/circle) arrangement \(E(m,n)\) that **never self‑cross** (touching at [lattice points](https://ourbigbook.com/codex/lattice-point) is allowed). The program outputs:

\[
L(6,10) \bmod 10^{10}.
\]

## Main techniques used

### 1) Reduce each lattice point to 4 “ports”

Each [lattice point](https://ourbigbook.com/codex/lattice-point) is incident to 8 arcs, but they come in 4 adjacent *pairs* (north/east/south/west): between two neighboring [lattice points](https://ourbigbook.com/codex/lattice-point) there are two distinct [circle](https://ourbigbook.com/codex/circle) arcs.

A non‑crossing traversal through a [vertex](https://ourbigbook.com/codex/vertex-graph-theory) can be described by how it groups these 4 directions into blocks (directions in the same block are connected together around the [vertex](https://ourbigbook.com/codex/vertex-graph-theory) without crossings).

The number of non‑crossing partitions of 4 items is **Catalan(4) = 14**, so there are only 14 legal local connection patterns to consider.

### 2) Frontier (transfer-matrix) dynamic programming

We sweep the \((n+1)\times(m+1)\) [lattice points](https://ourbigbook.com/codex/lattice-point) in [row-major order](https://ourbigbook.com/codex/row-major-order).

At any step, the boundary between processed/unprocessed [vertices](https://ourbigbook.com/codex/vertex-graph-theory) intersects the [graph](https://ourbigbook.com/codex/graph) in a small set of “open” connection stubs. The [DP](https://ourbigbook.com/codex/dynamic-programming) state records which stubs are connected together so far.

This is the same idea as [transfer-matrix methods](https://ourbigbook.com/codex/transfer-matrix-method) used for planar connectivity problems (e.g. [Hamiltonian cycles](https://ourbigbook.com/codex/hamiltonian-cycle) / loop models):

* `dp[state] = number of partial constructions producing this frontier connectivity`.
* At each [lattice point](https://ourbigbook.com/codex/lattice-point), try all 14 local patterns and update the frontier connectivity accordingly.

### 3) Compact connectivity encoding with relabeling

Connectivity is stored as a [sequence](https://ourbigbook.com/codex/sequence) of **4-bit labels (nibbles)** packed into a Python [integer](https://ourbigbook.com/codex/integer).

* Equal labels mean “these frontier positions belong to the same [connected component](https://ourbigbook.com/codex/connected-component)”.
* After each update, labels are canonicalized (“first-seen relabeling”) to keep the number of distinct states small.

This turns the [frontier DP](https://ourbigbook.com/codex/frontier-dp) into a fast dictionary-based computation.

### 4) Enforcing a single Eulerian cycle

If a [connected component](https://ourbigbook.com/codex/connected-component) disappears from the frontier before the very last [vertex](https://ourbigbook.com/codex/vertex-graph-theory), that would form a **closed loop** disconnected from the rest — invalid because the final object must be *one* [Eulerian cycle](https://ourbigbook.com/codex/eulerian-cycle).

So the transition logic forbids “closing” a component early; it is only allowed at the final [lattice point](https://ourbigbook.com/codex/lattice-point).

### 5) Memoization of local transitions

For a fixed frontier state, row position `y`, and whether we are on the outer boundary, the list of successor states is the same every time.

We cache these successor lists, which speeds up the run significantly.
