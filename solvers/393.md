# Project Euler 393 Solution - Migrating Ants

<https://projecteuler.net/problem=393>:

* [393.py](393.py)

## Problem Summary

Let $F(n)$ denote the number of valid migrations on an $n \times n$ grid. Every cell initially contains one ant, every ant must move to a neighboring cell, every cell must receive exactly one ant, and two ants are not allowed to traverse the same undirected [edge](https://ourbigbook.com/codex/edge-of-a-graph) in opposite directions. In [graph](https://ourbigbook.com/codex/graph) terms, each [vertex](https://ourbigbook.com/codex/vertex-of-a-graph) has [out-degree](https://ourbigbook.com/codex/out-degree) $1$ and [in-degree](https://ourbigbook.com/codex/in-degree) $1$, so a valid migration is a [disjoint union](https://ourbigbook.com/codex/disjoint-union) of [directed cycles](https://ourbigbook.com/codex/directed-cycle), with 2-cycles forbidden.

## Mathematical Approach

### Step 1: Convert the migration into two perfect matchings

Color the grid as a checkerboard, with black and white cells. Every legal move goes from one color to the other, because adjacent cells always have opposite [integer parity](https://ourbigbook.com/codex/integer-parity). Split the [directed edges](https://ourbigbook.com/codex/directed-edge) of a migration into two sets:

$$M_1=\{\text{moves from black to white}\},\qquad M_2=\{\text{moves from white to black}\}.$$

Now inspect $M_1$. Every black [vertex](https://ourbigbook.com/codex/vertex-of-a-graph) has exactly one outgoing move, so every black cell is incident to exactly one [edge](https://ourbigbook.com/codex/edge-of-a-graph) of $M_1$. Every white [vertex](https://ourbigbook.com/codex/vertex-of-a-graph) has exactly one incoming move, and the only possible source is a black neighbor, so every white cell is also incident to exactly one [edge](https://ourbigbook.com/codex/edge-of-a-graph) of $M_1$. Therefore $M_1$ is a [perfect matching](https://ourbigbook.com/codex/perfect-matching) of the [bipartite](https://ourbigbook.com/codex/bipartite-graph) [grid graph](https://ourbigbook.com/codex/grid-graph). By the same argument, $M_2$ is another [perfect matching](https://ourbigbook.com/codex/perfect-matching).

The forbidden “swap positions across one [edge](https://ourbigbook.com/codex/edge-of-a-graph)” condition says that the two [graph matchings](https://ourbigbook.com/codex/matching-graph-theory) may not use the same undirected [edge](https://ourbigbook.com/codex/edge-of-a-graph). Hence valid migrations are in [bijection](https://ourbigbook.com/codex/bijection) with [ordered pairs](https://ourbigbook.com/codex/ordered-pair) $(M_1,M_2)$ of edge-disjoint [perfect matchings](https://ourbigbook.com/codex/perfect-matching). This is the central reformulation used by all three solution files.

### Step 2: Immediate parity consequence

If $n$ is odd, the checkerboard coloring contains different numbers of black and white cells, namely

$$\left\lceil\frac{n^2}{2}\right\rceil \neq \left\lfloor\frac{n^2}{2}\right\rfloor.$$

A [perfect matching](https://ourbigbook.com/codex/perfect-matching) in a [bipartite graph](https://ourbigbook.com/codex/bipartite-graph) requires both [color classes](https://ourbigbook.com/codex/color-class) to have equal size, so for odd $n$ no [perfect matching](https://ourbigbook.com/codex/perfect-matching) exists at all. Therefore

$$F(n)=0\qquad\text{for odd }n.$$

The solver asserts this directly with the checkpoint $F(3)=0$.

### Step 3: Describe one row by a profile state

The implementations process the board row by row. For one [graph matching](https://ourbigbook.com/codex/matching-graph-theory) layer, consider a fixed row $r$. Some cells in that row may already be matched vertically to row $r-1$; the code records those columns by a [bitmask](https://ourbigbook.com/codex/bit-mask) $in$. If bit $c$ is set, then cell $(r,c)$ is already occupied in that [graph matching](https://ourbigbook.com/codex/matching-graph-theory) layer and needs no new decision inside the current row.

For Problem 393 we must track two [graph matching](https://ourbigbook.com/codex/matching-graph-theory) layers simultaneously, so the state is a pair $(in_1,in_2)$. The code packs it into one [integer](https://ourbigbook.com/codex/integer):

$$state = in_1 + (in_2 \ll n).$$

Here $in_1$ belongs to the black-to-white [graph matching](https://ourbigbook.com/codex/matching-graph-theory) and $in_2$ to the white-to-black [graph matching](https://ourbigbook.com/codex/matching-graph-theory). At the end of the row we obtain two new masks $(out_1,out_2)$, representing vertical [edges](https://ourbigbook.com/codex/edge-of-a-graph) that continue downward into row $r+1$.

### Step 4: Local choices for one cell

Inside one [graph matching](https://ourbigbook.com/codex/matching-graph-theory) layer, an unoccupied cell has only two possible ways to be matched while scanning left to right:

$$\text{horizontal to }(r,c+1)\qquad\text{or}\qquad \text{vertical to }(r+1,c).$$

If the cell is already covered by an incoming vertical [edge](https://ourbigbook.com/codex/edge-of-a-graph) from above, the only option is “filled”. On the last row, vertical placement is impossible because there is no row below.

This is exactly what the local `options` helper returns: `Filled`, `Horizontal`, or `Vertical`, together with the bit updates needed for the current occupancy mask and for the outgoing mask.

### Step 5: Why only two conflict checks are needed

Within one [graph matching](https://ourbigbook.com/codex/matching-graph-theory) layer, the occupancy mask already guarantees that each cell is used exactly once. Across the two layers, the only forbidden situation is reusing the same undirected [edge](https://ourbigbook.com/codex/edge-of-a-graph), because that would mean the two directed [graph matchings](https://ourbigbook.com/codex/matching-graph-theory) traverse it in opposite directions. For the current column $c$, that can happen in exactly two ways:

$$\text{both layers choose the same horizontal edge }(r,c)\text{--}(r,c+1),$$

$$\text{both layers choose the same vertical edge }(r,c)\text{--}(r+1,c).$$

That is why the [DFS](https://ourbigbook.com/codex/depth-first-search) rejects only the pairs `(Horizontal, Horizontal)` and `(Vertical, Vertical)` at the same column. No other cross-layer test is necessary.

### Step 6: Transfer recurrence

For fixed input masks $(in_1,in_2)$ and a flag telling us whether we are on the last row, the [depth-first search](https://ourbigbook.com/codex/depth-first-search) enumerates every legal filling of that row and counts how many of them lead to each output pair $(out_1,out_2)$. Let

$$T_{\mathrm{last}}((in_1,in_2)\to(out_1,out_2))$$

be that multiplicity. Then the row [DP](https://ourbigbook.com/codex/dynamic-programming) is

$$\mathrm{DP}_{r+1}(out_1,out_2)=\sum_{in_1,in_2}\mathrm{DP}_r(in_1,in_2)\,T_{\mathrm{last}(r)}((in_1,in_2)\to(out_1,out_2)).$$

The [initial condition](https://ourbigbook.com/codex/initial-condition) is

$$\mathrm{DP}_0(0,0)=1,$$

because before the first row there are no pending vertical [edges](https://ourbigbook.com/codex/edge-of-a-graph). The final answer is

$$F(n)=\mathrm{DP}_n(0,0),$$

because after the last row there must again be no unfinished vertical [edges](https://ourbigbook.com/codex/edge-of-a-graph).

### Worked Example: $n=2$

The $2 \times 2$ grid has exactly two [perfect matchings](https://ourbigbook.com/codex/perfect-matching): the two horizontal [edges](https://ourbigbook.com/codex/edge-of-a-graph), or the two vertical [edges](https://ourbigbook.com/codex/edge-of-a-graph). Since the two layers must be edge-disjoint, one layer must choose the horizontal [graph matching](https://ourbigbook.com/codex/matching-graph-theory) and the other must choose the vertical [graph matching](https://ourbigbook.com/codex/matching-graph-theory). The pair is ordered, so we get two possibilities:

$$F(2)=2.$$

These are precisely the clockwise and counterclockwise 4-cycles around the square, and they match the checkpoint `f(2)=2` in the repository code.

### How the Code Works

The Python solver stores the row frontier in a dictionary keyed by the packed profile state `in1 | (in2 << n)`. A cached `transitions` function expands one input state and the last-row flag into all possible output states for that row. It fills the row left to right, generates the legal options for each [graph matching](https://ourbigbook.com/codex/matching-graph-theory) layer, and rejects only the two edge-sharing conflicts: both layers choosing the same horizontal [edge](https://ourbigbook.com/codex/edge-of-a-graph) or both choosing the same vertical [edge](https://ourbigbook.com/codex/edge-of-a-graph).

After a row transition is known, the outer [DP](https://ourbigbook.com/codex/dynamic-programming) only multiplies the cached transition multiplicities by the number of ways to reach the input state. The code asserts $F(2)=2$, $F(3)=0$, and $F(4)=88$ before evaluating the target $F(10)$:

$$112398351350823112.$$

## Complexity Analysis

The profile space is a [subset](https://ourbigbook.com/codex/subset)

$$\mathcal{S}\subseteq \{0,1\}^n \times \{0,1\}^n,$$

so there are at most $2^{2n}$ combined masks. Building one uncached transition map is itself exponential in $n$, because the [DFS](https://ourbigbook.com/codex/depth-first-search) explores all legal row fillings for the two coupled [graph matching](https://ourbigbook.com/codex/matching-graph-theory) layers. However, each profile $(in_1,in_2,last\_row)$ is solved only once and then reused whenever it reappears in the outer [DP](https://ourbigbook.com/codex/dynamic-programming). Thus the [algorithm](https://ourbigbook.com/codex/algorithm) is exponential in the board width, but only linear in the number of rows after transition reuse. Memory usage is also exponential in $n$, dominated by the [DP](https://ourbigbook.com/codex/dynamic-programming) frontier and the cached transition tables. That is still practical for $n=10$, while direct enumeration over all neighbor choices would be completely infeasible.
