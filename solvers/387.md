# Project Euler 387 Solution - Harshad Numbers

<https://projecteuler.net/problem=387>:

* [387.py](387.py)

## Problem Summary

We want the sum of all [primes](https://ourbigbook.com/codex/prime) $p \lt L$ such that deleting the last [decimal digit](https://ourbigbook.com/codex/decimal-digit) of $p$ leaves a *strong right-truncatable [Harshad](https://ourbigbook.com/codex/harshad-number) number*. In the local solution files the default bound is $L = 10^{14}$.

Let $s(n)$ denote the sum of the [decimal digits](https://ourbigbook.com/codex/decimal-digit) of $n$. A [positive integer](https://ourbigbook.com/codex/positive-integer) $n$ is a [Harshad](https://ourbigbook.com/codex/harshad-number) number if

$$s(n)\mid n.$$

It is *strong* if

$$\frac{n}{s(n)}$$

is [prime](https://ourbigbook.com/codex/prime). It is *right-truncatable* if every non-empty decimal prefix is [Harshad](https://ourbigbook.com/codex/harshad-number). Writing $n=\overline{d_1d_2\cdots d_k}$, each prefix $\overline{d_1d_2\cdots d_i}$ for $1 \le i \le k$ must satisfy the [Harshad](https://ourbigbook.com/codex/harshad-number) [divisibility](https://ourbigbook.com/codex/divisibility) condition.

Every candidate answer [prime](https://ourbigbook.com/codex/prime) has a unique decomposition

$$p = 10h + d,\qquad d = p \bmod 10,\qquad h=\left\lfloor\frac{p}{10}\right\rfloor.$$

The problem therefore reduces to generating exactly those prefixes $h$ that are strong and right-truncatable [Harshad](https://ourbigbook.com/codex/harshad-number) numbers, then checking whether one more [digit](https://ourbigbook.com/codex/numerical-digit) turns them into a [prime](https://ourbigbook.com/codex/prime) below $L$.

## Mathematical Approach

### Step 1: Search the prefix, not the final prime

A brute-force approach would iterate over [primes](https://ourbigbook.com/codex/prime) $p \lt L$, remove the last [digit](https://ourbigbook.com/codex/numerical-digit), and test the whole prefix chain. The repository code does the opposite: it constructs only valid [Harshad](https://ourbigbook.com/codex/harshad-number) prefixes and never explores arbitrary [integers](https://ourbigbook.com/codex/integer).

All one-digit numbers $1,\dots,9$ are [Harshad](https://ourbigbook.com/codex/harshad-number) because for a single [decimal digit](https://ourbigbook.com/codex/decimal-digit) we have $s(n)=n$, hence $n/s(n)=1$. These values are the roots of the [search tree](https://ourbigbook.com/codex/search-tree).

### Step 2: Extend prefixes with a digit-sum recurrence

Suppose the current node is a [Harshad](https://ourbigbook.com/codex/harshad-number) number $n$ with [digit sum](https://ourbigbook.com/codex/digit-sum) $s=s(n)$. Appending a [digit](https://ourbigbook.com/codex/numerical-digit) $d\in\{0,1,\dots,9\}$ gives

$$n' = 10n + d,\qquad s(n') = s + d.$$

The child is useful only if it is [Harshad](https://ourbigbook.com/codex/harshad-number), namely

$$10n + d \equiv 0 \pmod{s+d}.$$

This test is exactly what the [DFS](https://ourbigbook.com/codex/depth-first-search) applies before recursing. Because every child is created from an already valid [Harshad](https://ourbigbook.com/codex/harshad-number) parent, right-truncatability is automatic by [induction](https://ourbigbook.com/codex/induction): each visited node has a [Harshad](https://ourbigbook.com/codex/harshad-number) parent chain all the way back to a one-digit root.

### Step 3: Identify strong Harshad prefixes immediately

Whenever a visited prefix $n \ge 10$ is [Harshad](https://ourbigbook.com/codex/harshad-number), the code computes

$$q=\frac{n}{s(n)}.$$

If $q$ is [prime](https://ourbigbook.com/codex/prime), then $n$ is strong. This is the decisive filter, because a final answer [prime](https://ourbigbook.com/codex/prime) must come from a strong prefix. One-digit prefixes are excluded from this stage in the code since they would only produce $q=1$, which is not [prime](https://ourbigbook.com/codex/prime).

### Step 4: Only four last digits can produce a prime

For any [prime](https://ourbigbook.com/codex/prime) $p \gt 10$, the last [digit](https://ourbigbook.com/codex/numerical-digit) cannot be even and cannot be $5$. Therefore every strong prefix $h$ produces at most four relevant [prime](https://ourbigbook.com/codex/prime) candidates:

$$p = 10h + d,\qquad d \in \{1,3,7,9\}.$$

The implementations test each such $p$ for the two remaining conditions: $p \lt L$ and $p$ is [prime](https://ourbigbook.com/codex/prime).

If both hold, $p$ is added to the total. This characterization is complete and duplicate-free, because decimal truncation is unique: every valid [prime](https://ourbigbook.com/codex/prime) determines exactly one prefix $h=\lfloor p/10 \rfloor$.

### Step 5: Bound the recursion by the largest useful prefix

If $p=10h+d \lt L$, then necessarily

$$h \le \left\lfloor\frac{L-1}{10}\right\rfloor.$$

The C++ solution stores this value in `harshad_limit`. Any [Harshad](https://ourbigbook.com/codex/harshad-number) number larger than this can never be the prefix of a valid answer, so exploring beyond it is pointless.

The recursive stop test in the code is slightly sharper. If

$$n \gt \left\lfloor\frac{\left\lfloor(L-1)/10\right\rfloor}{10}\right\rfloor,$$

then every child $10n+d$ already exceeds `harshad_limit`. The current node may still produce final [primes](https://ourbigbook.com/codex/prime) $10n+d$, but it cannot produce deeper [Harshad](https://ourbigbook.com/codex/harshad-number) prefixes that will later matter.

### Worked Example

Take $n=18$. Its [digit sum](https://ourbigbook.com/codex/digit-sum) is $s(18)=9$, and $18/9=2$, so $18$ is a strong [Harshad](https://ourbigbook.com/codex/harshad-number) number. Since $1$ and $18$ are both [Harshad](https://ourbigbook.com/codex/harshad-number), it is also right-truncatable.

The only possible [prime](https://ourbigbook.com/codex/prime) endings are

$$181,\ 183,\ 187,\ 189.$$

Among these, $181$ is [prime](https://ourbigbook.com/codex/prime), $183$ and $189$ are divisible by $3$, and $187=11\cdot 17$. Hence $181$ is one of the required [primes](https://ourbigbook.com/codex/prime).

The local C++ program also validates the sample checkpoint

$$\sum_{p \lt 10^4} p = 90619,$$

and then cross-checks the optimized solver against a brute-force routine at $L=10^6$. Those checks are consistent with the derivation above.

## How the Code Works

The three local implementations use the same core state: the current prefix $n$ and its [digit sum](https://ourbigbook.com/codex/digit-sum) $s(n)$. Carrying the [digit sum](https://ourbigbook.com/codex/digit-sum) forward via $s(n')=s(n)+d$ makes each tree transition constant time instead of recomputing all [decimal digits](https://ourbigbook.com/codex/decimal-digit) from scratch.

The C++ file exposes `solve(limit)`, optional argument parsing with `--limit=...`, and a `--skip-checkpoints` flag. Its [DFS](https://ourbigbook.com/codex/depth-first-search) function `dfs_harshad` returns the sum contributed by one subtree. For [primality](https://ourbigbook.com/codex/primality) it first removes small [prime](https://ourbigbook.com/codex/prime) [divisors](https://ourbigbook.com/codex/divisor) up to $37$, then runs deterministic [Miller-Rabin](https://ourbigbook.com/codex/miller-rabin-primality-test) with bases

$$\{2,3,5,7,11,13,17\}.$$

To avoid overflow in modular multiplication, C++ uses `__uint128_t`.

The Python file implements the same [recurrence relation](https://ourbigbook.com/codex/recurrence-relation) and the same [Miller-Rabin](https://ourbigbook.com/codex/miller-rabin-primality-test) base set, but accumulates the answer in a `nonlocal` variable inside `dfs`. The Java file mirrors the same [DFS](https://ourbigbook.com/codex/depth-first-search) structure in `dfsHarshad` and delegates [modular exponentiation](https://ourbigbook.com/codex/modular-exponentiation) to `BigInteger.modPow`. Mathematically all three versions are identical.

## Complexity Analysis

Let $H(L)$ be the number of right-truncatable [Harshad](https://ourbigbook.com/codex/harshad-number) prefixes actually visited, and let $S(L)$ be the number of those prefixes that are strong. The [DFS](https://ourbigbook.com/codex/depth-first-search) work per visited node is $O(1)$: one [digit-sum](https://ourbigbook.com/codex/digit-sum) update and one [divisibility](https://ourbigbook.com/codex/divisibility) test for each appended [digit](https://ourbigbook.com/codex/numerical-digit).

Each strong prefix triggers at most four [primality tests](https://ourbigbook.com/codex/primality-test), so a precise description is

$$O\bigl(H(L) + 4S(L)\,T_{\mathrm{prime}}\bigr),$$

where $T_{\mathrm{prime}}$ is the cost of one [Miller-Rabin](https://ourbigbook.com/codex/miller-rabin-primality-test) test in the 64-bit range used here. Since $S(L)\le H(L)$, this is often summarized as

$$O\bigl(H(L)\,T_{\mathrm{prime}}\bigr).$$

The [recursion](https://ourbigbook.com/codex/recursion) depth is the number of [decimal digits](https://ourbigbook.com/codex/decimal-digit) of the largest explored prefix, so the auxiliary stack space is $O(\log_{10} L)$. This is far smaller than scanning all [integers](https://ourbigbook.com/codex/integer) or all [primes](https://ourbigbook.com/codex/prime) below $L$.
