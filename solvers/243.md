# Project Euler 243 Solution - Resilience

<https://projecteuler.net/problem=243>:

* [243.py](243.py)

## Problem Summary

For a fixed [denominator](https://ourbigbook.com/codex/denominator) $d$, the proper fractions are

$$\frac{1}{d},\frac{2}{d},\dots,\frac{d-1}{d}.$$

A proper fraction is resilient exactly when it is already in lowest terms, so the number of resilient fractions with [denominator](https://ourbigbook.com/codex/denominator) $d$ is $\varphi(d)$. Therefore the [resilience](https://ourbigbook.com/codex/resilience-of-a-denominator) of $d$ is

$$R(d)=\frac{\varphi(d)}{d-1}.$$

The goal is to find the smallest [denominator](https://ourbigbook.com/codex/denominator) $d$ such that

$$R(d) \lt \frac{15499}{94744}.$$

[Brute force](https://ourbigbook.com/codex/brute-force-search) is a poor fit, because most [denominators](https://ourbigbook.com/codex/denominator) are obviously far from optimal. The successful approach is to search directly through the [prime factorizations](https://ourbigbook.com/codex/prime-factorization) that can plausibly minimize $d$.

## Mathematical Approach

The decisive fact is that [resilience](https://ourbigbook.com/codex/resilience-of-a-denominator) is governed much more by the distinct [prime](https://ourbigbook.com/codex/prime) [divisors](https://ourbigbook.com/codex/divisor) of $d$ than by their exponents. The implementations are built around that separation.

### From resilient fractions to the totient function

A [numerator](https://ourbigbook.com/codex/numerator) $n$ gives a resilient fraction $n/d$ precisely when $\gcd(n,d)=1$. Among the $d-1$ possible [numerators](https://ourbigbook.com/codex/numerator) $1 \le n \lt d$, exactly $\varphi(d)$ are [coprime](https://ourbigbook.com/codex/coprime) to $d$. That turns the original counting problem into a purely multiplicative number-theory problem: once $\varphi(d)$ is known, the [resilience](https://ourbigbook.com/codex/resilience-of-a-denominator) follows immediately.

### Prime factorization separates the distinct primes from the exponents

If

$$d=\prod_{i=1}^{k} p_i^{e_i},$$

then Euler's [product formula](https://ourbigbook.com/codex/product-formula) gives

$$\varphi(d)=d\prod_{i=1}^{k}\left(1-\frac{1}{p_i}\right)=\prod_{i=1}^{k} p_i^{e_i-1}(p_i-1).$$

Hence

$$R(d)=\frac{d}{d-1}\prod_{i=1}^{k}\left(1-\frac{1}{p_i}\right).$$

This identity is the heart of the search. The product $\prod (1-1/p_i)$ depends only on which [primes](https://ourbigbook.com/codex/prime) divide $d$, not on how large the exponents are. Raising an exponent does not change $\varphi(d)/d$; it only replaces the prefactor $d/(d-1)$ by a slightly smaller number that is closer to 1. So introducing a new distinct [prime](https://ourbigbook.com/codex/prime) causes the main drop in [resilience](https://ourbigbook.com/codex/resilience-of-a-denominator), while increasing an existing exponent is a fine-tuning move once the [denominator](https://ourbigbook.com/codex/denominator) is already close to the target.

This also explains why the search starts with the smallest [primes](https://ourbigbook.com/codex/prime). A new [prime](https://ourbigbook.com/codex/prime) $p$ multiplies $\varphi(d)/d$ by $1-1/p$, and that reduction is strongest for small $p$. Minimal candidates therefore come from products of consecutive small [primes](https://ourbigbook.com/codex/prime), possibly followed by extra powers of those same [primes](https://ourbigbook.com/codex/prime).

### Why only canonical exponent vectors need to be searched

Suppose two [primes](https://ourbigbook.com/codex/prime) satisfy $p \lt q$, and two exponents satisfy $a \gt b$. Then

$$p^a q^b \lt p^b q^a.$$

So if a [denominator](https://ourbigbook.com/codex/denominator) uses the same two [primes](https://ourbigbook.com/codex/prime) and the same two exponents, it is always smaller when the larger exponent is attached to the smaller [prime](https://ourbigbook.com/codex/prime). More generally, for a fixed set of [primes](https://ourbigbook.com/codex/prime) and a fixed multiset of exponents, the smallest [denominator](https://ourbigbook.com/codex/denominator) is obtained when the exponents are non-increasing along the increasing [prime](https://ourbigbook.com/codex/prime) list:

$$e_1 \ge e_2 \ge e_3 \ge \cdots.$$

That ordering is not merely a convenience. It is a correctness argument for the [DFS](https://ourbigbook.com/codex/depth-first-search): any candidate that breaks this rule can be rearranged into a smaller [denominator](https://ourbigbook.com/codex/denominator) with the same distinct-prime set, so it cannot be the minimal solution.

### Exact comparison and a worked example

Instead of dividing, the implementations test the target inequality as

$$\varphi(d)\cdot 94744 \lt 15499\cdot(d-1).$$

This avoids floating-point rounding and keeps the search exact.

A small checkpoint illustrates the mechanism. If the threshold were $4/10$, then $d=6=2\cdot 3$ gives

$$\varphi(6)=2,\qquad R(6)=\frac{2}{5}=\frac{4}{10},$$

so the strict inequality still fails. But $d=12=2^2\cdot 3$ gives

$$\varphi(12)=4,\qquad R(12)=\frac{4}{11}\lt\frac{4}{10}.$$

That is exactly the pattern exploited in the full problem: a [squarefree](https://ourbigbook.com/codex/squarefree-integer) product of small [primes](https://ourbigbook.com/codex/prime) pushes the [resilience](https://ourbigbook.com/codex/resilience-of-a-denominator) down quickly, and then an extra power of a small [prime](https://ourbigbook.com/codex/prime) can be the final adjustment that crosses the line with the smallest possible [denominator](https://ourbigbook.com/codex/denominator).

## How the Code Works

The C++, Python, and Java implementations perform a [depth-first search](https://ourbigbook.com/codex/depth-first-search) over increasing [primes](https://ourbigbook.com/codex/prime). The state carried by the [recursion](https://ourbigbook.com/codex/recursion) is the current [denominator](https://ourbigbook.com/codex/denominator) $d$, the current [totient](https://ourbigbook.com/codex/euler-s-totient-function) $\varphi(d)$, the position in the [prime](https://ourbigbook.com/codex/prime) list, the maximum exponent allowed for the next [prime](https://ourbigbook.com/codex/prime), and the best valid [denominator](https://ourbigbook.com/codex/denominator) found so far.

### Incremental totient updates

The search never recomputes $\varphi(d)$ from scratch. When a [prime](https://ourbigbook.com/codex/prime) $p$ is attached for the first time, the update is

$$d \leftarrow dp,\qquad \varphi(d)\leftarrow \varphi(d)(p-1).$$

If the same [prime](https://ourbigbook.com/codex/prime) is extended from exponent $e$ to exponent $e+1$, the update becomes

$$d \leftarrow dp,\qquad \varphi(d)\leftarrow \varphi(d)p.$$

Those two rules are the main [invariant](https://ourbigbook.com/codex/invariant-mathematics) of the [recursion](https://ourbigbook.com/codex/recursion) and come directly from the prime-power formula for $\varphi$.

### Why the search tree stays small

At each node, the implementation first checks whether the current [denominator](https://ourbigbook.com/codex/denominator) already meets the target. If it does, that [denominator](https://ourbigbook.com/codex/denominator) becomes the new global best and the branch stops, because multiplying by more [primes](https://ourbigbook.com/codex/prime) can only increase $d$. If the current [denominator](https://ourbigbook.com/codex/denominator) is already at least as large as the best known answer, the branch is also discarded immediately.

The next [recursive call](https://ourbigbook.com/codex/recursive-call) receives the current exponent as the [upper bound](https://ourbigbook.com/codex/upper-bound) for the next [prime](https://ourbigbook.com/codex/prime), enforcing the canonical condition $e_1 \ge e_2 \ge \cdots$. This removes duplicate exponent [permutations](https://ourbigbook.com/codex/permutation) automatically. The implementations only need a short initial list of consecutive [primes](https://ourbigbook.com/codex/prime), up to 31, because the optimum is found inside that heavily pruned search space. The C++ implementation widens the cross-multiplication to 128-bit [integer arithmetic](https://ourbigbook.com/codex/integer-arithmetic), Python uses arbitrary-precision [integers](https://ourbigbook.com/codex/integer), and Java remains safely within 64-bit range for this target.

## Complexity Analysis

Without pruning, the problem is combinatorial in the possible [exponent vectors](https://ourbigbook.com/codex/exponent-vector). A useful way to describe the explored set is: the [DFS](https://ourbigbook.com/codex/depth-first-search) visits only tuples

$$e_1 \ge e_2 \ge \cdots \ge 0,\qquad \prod_i p_i^{e_i} \lt d_{\text{best}},$$

where $d_{\text{best}}$ is the best [denominator](https://ourbigbook.com/codex/denominator) known at that stage of the search. The exponent-order restriction removes all reorderings of the same multiset, and the best-value bound cuts off large branches before they expand.

[Memory usage](https://ourbigbook.com/codex/memory-usage) is $O(k)$, where $k$ is the [recursion](https://ourbigbook.com/codex/recursion) depth, because only one search path is stored at a time. For the actual target, $k$ is a small constant and the visited tree is tiny in practice. The [algorithm](https://ourbigbook.com/codex/algorithm) is fast precisely because it searches near-optimal [integer factorizations](https://ourbigbook.com/codex/integer-factorization) instead of scanning all [integers](https://ourbigbook.com/codex/integer).
