# Project Euler 263 Solution - An Engineers' Dream Come True

<https://projecteuler.net/problem=263>:

* [263.py](263.py)

This repository contains a Python solution for **Project Euler 263**.

We need the first four [integers](https://ourbigbook.com/codex/integer) `n` such that:

- `n-9, n-3, n+3, n+9` are **four consecutive [primes](https://ourbigbook.com/codex/prime)** with gaps `6, 6, 6` (a “triple [sexy prime pair](https://ourbigbook.com/codex/sexy-prime-pair)”), and
- `n-8, n-4, n, n+4, n+8` are all **[practical numbers](https://ourbigbook.com/codex/practical-number)**.

The program prints the sum of those four `n`.

## Main techniques

### 1) Candidate generation from prime-gap patterns
A triple [sexy-pair](https://ourbigbook.com/codex/sexy-prime-pair) is exactly the situation where four **consecutive** [primes](https://ourbigbook.com/codex/prime) have gaps

```
6, 6, 6
```

So we stream [primes](https://ourbigbook.com/codex/prime) in order and keep a sliding window of the last four [primes](https://ourbigbook.com/codex/prime). When their differences match `6,6,6`, we immediately know the corresponding candidate is:

- `n = (n-3) + 3 = p1 + 3`

where `p1` is the second [prime](https://ourbigbook.com/codex/prime) in that window.

This avoids scanning all [integers](https://ourbigbook.com/codex/integer) and only triggers further work on rare [prime constellations](https://ourbigbook.com/codex/prime-constellation).

### 2) Segmented sieve to stream primes up to ~1e9
Storing a full [number-theoretic sieve](https://ourbigbook.com/codex/number-theoretic-sieve) up to the required limit would be too large. Instead, the code uses an **odd-only [segmented sieve](https://ourbigbook.com/codex/segmented-sieve)**:

- precompute base [primes](https://ourbigbook.com/codex/prime) up to `sqrt(high)`
- mark [composites](https://ourbigbook.com/codex/composite-number) inside a fixed-size [interval](https://ourbigbook.com/codex/interval) `[low, high)`
- emit [primes](https://ourbigbook.com/codex/prime) from that [interval](https://ourbigbook.com/codex/interval), then move to the next segment

This keeps memory usage small while still being fast.

### 3) Practical numbers via the Stewart–Sierpiński characterization
Checking the definition of “[practical](https://ourbigbook.com/codex/practical-number)” directly is expensive. The code uses a known theorem:

If

```
n = p1^a1 * p2^a2 * ... * pk^ak   (p1 < p2 < ...)
```

then `n` is [practical](https://ourbigbook.com/codex/practical-number) iff:

- `p1 = 2`, and
- for each `i > 1`: `pi <= 1 + σ(p1^a1 * ... * p(i-1)^a(i-1))`

where `σ` is the [sum-of-divisors function](https://ourbigbook.com/codex/sum-of-divisors-function).

So the implementation:

1. factors `n` by [trial division](https://ourbigbook.com/codex/trial-division) over small [primes](https://ourbigbook.com/codex/prime)
2. walks the factors in increasing order while maintaining the prefix `σ`

This makes each [practical](https://ourbigbook.com/codex/practical-number) check very fast.

### 4) Small optimizations
- A fast necessary filter `n % 4 == 0` is applied before doing any factorization work.
- [Practical-number](https://ourbigbook.com/codex/practical-number) results are memoized in a dictionary, since nearby candidates may reuse values.
