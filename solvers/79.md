# Project Euler 79 Solution - Passcode Derivation

<https://projecteuler.net/problem=79>:

* [79.py](79.py)
* [79.lean](79.lean)

This is a **shortest common supersequence** problem: every login attempt must appear in the passcode in order, with gaps allowed. For example, `135` is a subsequence of `12345`, but is not a contiguous substring.

Requiring contiguous fragments instead gives the **shortest common superstring** problem, a [classical model of genome assembly](https://doi.org/10.1093/bioinformatics/btw450). P79 has a different bioinformatics connection: in [parallel DNA synthesis](https://arxiv.org/abs/2405.17499), a common supersequence describes nucleotide-addition steps that can produce all the desired strands, and shortening it reduces the number of steps.

Each successful login attempt is a 3-digit [string](https://ourbigbook.com/codex/string) `abc` meaning:

- `a` appears before `b`
- `b` appears before `c`

These are precedence constraints. Collect all [digits](https://ourbigbook.com/codex/numerical-digit) that appear, build a [directed graph](https://ourbigbook.com/codex/directed-graph) with [edges](https://ourbigbook.com/codex/edge) for each constraint (e.g., `a -> b`, `b -> c`), and then compute a **[topological ordering](https://ourbigbook.com/codex/topological-ordering)** of this [graph](https://ourbigbook.com/codex/graph).

For the supplied keylog, this graph is acyclic, so a valid [topological order](https://ourbigbook.com/codex/topological-order) uses each observed digit exactly once. Every valid passcode must include each observed digit at least once, making this ordering shortest. The provided solution uses [Kahn's algorithm](https://ourbigbook.com/codex/kahn-s-algorithm) (indegree-based [topological sort](https://ourbigbook.com/codex/topological-sorting)) with a [heap](https://ourbigbook.com/codex/heap) to select the lexicographically least ordering.

The solver implements this distinct-digit variant. General supersequence inputs can require repeated digits: attempts `123` and `231` fit in `1231`, although their digit-precedence graph has a cycle. Topological sorting alone does not solve that general case.

The [Lean source-level equivalence proofs](79.py.lean.attempt) cover list and tuple inputs. The stronger claim that arbitrary iterable inputs produce identical observations under every pair of traversal orders is false: on the set `{"", "x"}`, the first invalid attempt determines the exception message. [The source-level counterexample](79.py.lean.attempt) proves both complete executions on the same valid modeled heap. This does not distinguish the algorithms when they receive the same input order.

The [finite-set source proofs](79.py.lean.attempt) establish guaranteed `Equiv` for sets of valid attempts, even when the two calls choose different traversal orders. For arbitrary finite sets of strings, including invalid attempts, the separate `PossibleEquiv` relation matches their possible behaviors. Both calls terminate under every schedule and preserve caller-visible memory; matching input orders gives the same returned value or exact exception. The two-string counterexample above satisfies this relation while failing guaranteed `Equiv`. General custom-iterator equivalence remains unfinished.

The [complete-call result](79.py.lean.d/AllocationResult.lean) establishes `Equiv` for a shared choice schedule from the actual `solve` and `naive` calls through initialization, acquisition, validation, graph construction and topological sorting. It compares the passcode or exact graph-cycle error together with caller-visible objects, aliases and cycles. The [terminal-call proofs](79.py.lean.d/AllocationTerminal.lean) cover an ordinary iterator exception or the first invalid string after any finite valid prefix, without assuming anything about later iteration.

[Acquisition](79.py.lean.d/Acquisition.lean) and [accepted traversal](79.py.lean.d/Allocation.lean) may allocate repeatedly, including during exhaustion. Supported traces combine segments with unchanged caller heap size and explicit allocation steps for lists, tuples, bytearrays, sets, dictionary displays with scalar keys, `dict()` constructors, or instances. Acquisition may return the iterable itself or a fresh iterator, including construction through `__init__` with arguments. Initializer bodies use the same trace rules; there is no bound on steps or yields.

The regressions prove complete traversals for every natural input count: [a factory creates a fresh counter](../data/project-euler-statements/formalsw/tests/py/iterator_instance_checks), while [another counter allocates a cyclic dictionary before every yield and final exception](../data/project-euler-statements/formalsw/tests/py/iterator_dictionary_checks). Additional allocating instructions and divergence remain unfinished.

[Set construction](../data/project-euler-statements/formalsw/tests/py/iterator_set_construction_checks) covers displays, `set()` and `set(source)` for modeled source types. Its proofs retain shared tuple representatives and private consumer storage, including after a later unhashable item leaves a partially populated set. [Dictionary construction](../data/project-euler-statements/formalsw/tests/py/iterator_dictionary_construction_checks) also preserves shallow copies and private storage when a later input row fails. Custom mapping protocols and set traversal as dictionary-constructor inputs remain unsupported.

[Sequence construction](../data/project-euler-statements/formalsw/tests/py/iterator_sequence_construction_checks) covers `list()` and `tuple()` conversions from modeled built-in sources and reversed list copies. The proofs preserve shallow aliases and private consumer objects, distinguish fresh tuples from identity-preserving copies and empty-tuple interning, and cover arbitrary finite yielding prefixes. Custom iteration inside these conversions remains unsupported. [List and tuple slicing](../data/project-euler-statements/formalsw/tests/py/iterator_slice_checks) also covers arbitrary bounds and strides, full tuple identity and zero-step errors, with private storage preserved across repeated list slices.

[Bytearray construction and slicing](../data/project-euler-statements/formalsw/tests/py/iterator_buffer_checks) preserve private consumer objects across fresh copies, arbitrary finite yielding prefixes, and errors before allocation. The constructor proofs cover nonnegative integer and Boolean sizes and supported byte sources. Encoding forms and custom iteration during conversion remain unsupported.

Generated dataclass constructors are also covered, including frozen records and fields that refer to existing caller objects. [The dataclass iterator regression](../data/project-euler-statements/formalsw/tests/py/iterator_dataclass_checks) proves acquisition and arbitrary finite yielding prefixes while retaining aliases and the solver's private data. These source proofs do not yet enable unrestricted custom iterators in the public frontend.

The final failing or rejected yielding call can use the broader supported execution rules because no private consumer state is needed afterward. Acquisition failures also have [complete-call equivalence proofs](79.py.lean.attempt): method-lookup errors, exceptions raised by `__iter__`, and invalid returned iterators retain the same error and caller-visible object graph, including newly allocated cycles. Acquisition `StopIteration` propagates as an error rather than silently ending the loop.

The Python-specific proof is split between the equivalence results above and [execution lemmas](79.py.lean.d/Execution.lean). With dependencies cached, rebuilding the equivalence results takes about 4.5 seconds instead of 22 seconds for the combined file; both checks use about 2.2 GiB. Shared mathematical lemmas remain in the Lean libraries.
