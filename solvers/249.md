# Project Euler 249 Solution - Prime Subset Sums

<https://projecteuler.net/problem=249>:

* [249.py](249.py)

## Problem Summary

Let $\mathcal{P}$ be the set of all [primes](https://ourbigbook.com/codex/prime) below 5000. There are 669 such [primes](https://ourbigbook.com/codex/prime), so a [brute-force search](https://ourbigbook.com/codex/brute-force-search) would have to reason about $2^{669}$ different subsets. For each subset $A \subseteq \mathcal{P}$, form the sum $\sum_{p \in A} p$. The task is to count how many subsets have a [prime-valued sum](https://ourbigbook.com/codex/prime-valued-sum) and report that count [modulo](https://ourbigbook.com/codex/modulo-operation) $10^{16}$.

The count is over subsets, not over distinct sums. If two different subsets produce the same [prime](https://ourbigbook.com/codex/prime) total, both must be counted. The empty subset contributes the sum 0, which is not [prime](https://ourbigbook.com/codex/prime), so it never enters the final answer, but it is still the correct [base case](https://ourbigbook.com/codex/base-case) for the [recurrence relation](https://ourbigbook.com/codex/recurrence-relation).

## Mathematical Approach

The natural [state space](https://ourbigbook.com/codex/state-space) is the set of all achievable [subset sums](https://ourbigbook.com/codex/subset-sum). Since every input value is itself [prime](https://ourbigbook.com/codex/prime) and may be chosen at most once, the problem is a counting version of 0/1 [subset sum](https://ourbigbook.com/codex/subset-sum) rather than an unbounded partition problem.

### The generating function for subset sums

Order the input [primes](https://ourbigbook.com/codex/prime) increasingly as

$$p_1 < p_2 < \cdots < p_m,\qquad m=669.$$

If

$$G(x)=\prod_{i=1}^{m}(1+x^{p_i}),$$

then choosing the term $1$ means “do not use $p_i$”, while choosing $x^{p_i}$ means “use $p_i$ once”. Therefore

$$G(x)=\sum_{s=0}^{S_{\max}} F(s)x^s,$$

where $F(s)$ is exactly the number of subsets whose elements sum to $s$, and

$$S_{\max}=\sum_{p\in\mathcal{P}} p = 1{,}548{,}136.$$

The required answer is then

$$\text{Answer}=\sum_{\substack{q \text{ prime} \\ 0 \le q \le S_{\max}}} F(q)\pmod{10^{16}}.$$

### The recurrence after the first $k$ primes

Let $F_k(s)$ be the number of subsets of $\{p_1,\dots,p_k\}$ whose sum is $s$. Then

$$F_0(0)=1,\qquad F_0(s)=0 \text{ for } s>0,$$

and for $k\ge 1$, each subset counted by $F_k(s)$ either omits $p_k$ or includes it exactly once. That gives the [recurrence relation](https://ourbigbook.com/codex/recurrence-relation)

$$F_k(s)=F_{k-1}(s)+F_{k-1}(s-p_k),$$

where the second term is interpreted as 0 when $s<p_k$. This is the whole mathematics behind the [dynamic program](https://ourbigbook.com/codex/dynamic-program): every valid subset of the first $k$ [primes](https://ourbigbook.com/codex/prime) appears in exactly one of those two disjoint cases.

### Why one descending array is enough

The implementations do not store the full two-dimensional table. Instead, they keep a single array of coefficients and update it in descending order of $s$. After the first $k-1$ [primes](https://ourbigbook.com/codex/prime), suppose the array stores $F_{k-1}(s)$. When processing $p_k$, the update

$$F(s+p_k)\leftarrow F(s+p_k)+F(s)\pmod{10^{16}}$$

must read the old value of $F(s)$, not a value already modified by the same [prime](https://ourbigbook.com/codex/prime). Sweeping $s$ downward guarantees exactly that, so each [prime](https://ourbigbook.com/codex/prime) is used either zero times or one time, never twice in the same stage.

A second [invariant](https://ourbigbook.com/codex/invariant-mathematics) is that after the first $k$ [primes](https://ourbigbook.com/codex/prime), all nonzero entries lie in

$$0 \le s \le \sigma_k,\qquad \sigma_k=p_1+\cdots+p_k.$$

This explains why the code only iterates over the currently reachable frontier instead of scanning the whole array after every [prime](https://ourbigbook.com/codex/prime).

### Worked example: primes below 10

For the smaller set $\{2,3,5,7\}$, the [generating function](https://ourbigbook.com/codex/generating-function) is

$$G(x)=(1+x^2)(1+x^3)(1+x^5)(1+x^7).$$

Expanding it gives

$$G(x)=1+x^2+x^3+2x^5+2x^7+x^8+x^9+2x^{10}+2x^{12}+x^{14}+x^{15}+x^{17}.$$

The [prime](https://ourbigbook.com/codex/prime) exponents are $2,3,5,7,17$, with coefficients $1,1,2,2,1$. Therefore the number of subsets with [prime-valued sum](https://ourbigbook.com/codex/prime-valued-sum) is

$$1+1+2+2+1=7.$$

This example also shows why we count subsets rather than distinct sums: the coefficient of $x^5$ is 2 because both $\{5\}$ and $\{2,3\}$ produce the [prime-valued sum](https://ourbigbook.com/codex/prime-valued-sum) 5.

### From subset counts to the final total

Once every coefficient $F(s)$ has been computed [modulo](https://ourbigbook.com/codex/modulo-operation) $10^{16}$, the remaining task is only to know which indices $s$ are [prime](https://ourbigbook.com/codex/prime). That is why the solution performs a second [number-theoretic sieve](https://ourbigbook.com/codex/number-theoretic-sieve) up to $S_{\max}$: it marks [prime-valued sums](https://ourbigbook.com/codex/prime-valued-sum) once, then adds the stored subset counts at exactly those indices.

## How the Code Works

### Building the prime input set

The C++, Python, and Java implementations first run a [number-theoretic sieve](https://ourbigbook.com/codex/number-theoretic-sieve) up to 5000 to list the input [primes](https://ourbigbook.com/codex/prime). During that same pass they accumulate the total sum $S_{\max}$, which determines the length of the [dynamic programming](https://ourbigbook.com/codex/dynamic-programming) array.

### Running the one-dimensional counting DP

The array starts with one nonzero entry: there is exactly one way to make sum 0 before any [prime](https://ourbigbook.com/codex/prime) has been processed. Then each [prime](https://ourbigbook.com/codex/prime) is folded in by a descending sweep over currently reachable sums. If a sum $s$ already has $c$ representations, then $s+p$ gains another $c$ representations by appending the new [prime](https://ourbigbook.com/codex/prime) $p$.

Every entry is reduced [modulo](https://ourbigbook.com/codex/modulo-operation) $10^{16}$ immediately, so the code never needs the astronomically large exact counts. In the fixed-width implementations this is especially convenient: each update combines two [remainders](https://ourbigbook.com/codex/remainder) below $10^{16}$, which comfortably fits in 64-bit arithmetic.

### Filtering by prime totals

After the subset-count array has been completed, the implementation runs another [number-theoretic sieve](https://ourbigbook.com/codex/number-theoretic-sieve), now on the interval from 0 to $S_{\max}$. This second [number-theoretic sieve](https://ourbigbook.com/codex/number-theoretic-sieve) is about the possible [subset sums](https://ourbigbook.com/codex/subset-sum), not about the input [primes](https://ourbigbook.com/codex/prime). A final linear pass adds the counts stored at [prime](https://ourbigbook.com/codex/prime) indices only.

The small sanity cases are consistent across the implementations: using [primes](https://ourbigbook.com/codex/prime) below 10 gives 7, and using [primes](https://ourbigbook.com/codex/prime) below 20 gives 65. Those checks confirm that the [recurrence relation](https://ourbigbook.com/codex/recurrence-relation) and the prime-sum filter are aligned correctly.

## Complexity Analysis

If $m=\pi(5000)=669$ and $S_{\max}=1{,}548{,}136$, the [dynamic program](https://ourbigbook.com/codex/dynamic-program) costs $O(mS_{\max})$ time and $O(S_{\max})$ memory. The final [number-theoretic sieve](https://ourbigbook.com/codex/number-theoretic-sieve) on [subset sums](https://ourbigbook.com/codex/subset-sum) costs $O(S_{\max}\log\log S_{\max})$, which is smaller than the [DP](https://ourbigbook.com/codex/dynamic-programming) term at this scale.

So the problem is solved with one large but manageable one-dimensional table instead of enumerating $2^{669}$ subsets. That is the decisive reduction: [exponential search](https://ourbigbook.com/codex/exponential-search) over subsets becomes [polynomial](https://ourbigbook.com/codex/polynomial) counting over reachable sums.
