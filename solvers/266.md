# Project Euler 266 Solution - Pseudo Square Root

<https://projecteuler.net/problem=266>:

* [266.py](266.py)

## Problem Summary

Let

$$P=\prod_{p<190} p.$$

We want the largest [divisor](https://ourbigbook.com/codex/divisor) $d\mid P$ such that $d\le \sqrt P$. This [divisor](https://ourbigbook.com/codex/divisor) is the pseudo [square root](https://ourbigbook.com/codex/square-root) of $P$. The implementation finally prints the value [modulo](https://ourbigbook.com/codex/modulo) $10^{16}$, but the search itself is done exactly.

## Mathematical Approach

### 1. Divisors as Subset Products

Because $P$ is a product of distinct [primes](https://ourbigbook.com/codex/prime), every [divisor](https://ourbigbook.com/codex/divisor) corresponds to a subset of the [prime](https://ourbigbook.com/codex/prime) list. If $S$ is the chosen subset, then

$$d=\prod_{p\in S} p.$$

The condition $d\le \sqrt P$ is equivalent to

$$d^2\le P.$$

So the problem is a subset-product [maximization problem](https://ourbigbook.com/codex/maximization-problem) under an [upper bound](https://ourbigbook.com/codex/upper-bound).

### 2. Logarithms Turn the Product Constraint into a Sum Constraint

Multiplication is awkward to compare directly, but [logarithms](https://ourbigbook.com/codex/logarithm) convert products into sums:

$$\log d=\sum_{p\in S}\log p,\qquad \log d\le \tfrac12\log P.$$

That means we want a subset whose log-sum is as close as possible to $\tfrac12\log P$ from below. This is exactly the shape of a knapsack-style search.

### 3. Meet-in-the-Middle

The [prime](https://ourbigbook.com/codex/prime) list below 190 has 42 elements, so a [brute-force](https://ourbigbook.com/codex/brute-force-search) scan over all $2^{42}$ subsets is too large. The code splits the [primes](https://ourbigbook.com/codex/prime) into two halves, enumerates all [subset sums](https://ourbigbook.com/codex/subset-sum) in each half, sorts those lists, and then combines them efficiently.

For a left subset $a$ and a right subset $b$, the candidate is valid when

$$\log a+\log b\le \tfrac12\log P.$$

Among all valid pairs, we need the one with the greatest total [logarithm](https://ourbigbook.com/codex/logarithm).

### 4. Exact Validation After Log Filtering

[Floating-point](https://ourbigbook.com/codex/floating-point-representation) logs are used only to narrow the search. They do not decide the final answer. Once the [algorithm](https://ourbigbook.com/codex/algorithm) finds a near-optimal pair of masks, it reconstructs the exact product with [big integers](https://ourbigbook.com/codex/big-integer) and checks

$$d^2\le P$$

using exact arithmetic. This avoids [rounding errors](https://ourbigbook.com/codex/round-off-error) and guarantees the final [divisor](https://ourbigbook.com/codex/divisor) is truly maximal.

### 5. Why the Search Is Efficient

Each half has roughly $2^{21}$ subsets. Enumerating both halves is still feasible, especially because subset log sums can be built incrementally from [bit masks](https://ourbigbook.com/codex/bit-mask):

if a mask removes its lowest [set](https://ourbigbook.com/codex/set) [bit](https://ourbigbook.com/codex/bit), the new [subset sum](https://ourbigbook.com/codex/subset-sum) is the previous sum plus the log of the corresponding [prime](https://ourbigbook.com/codex/prime).

After sorting, the code uses a [monotone](https://ourbigbook.com/codex/monotonicity) scan over the two lists, then inspects a small neighborhood of right-hand candidates around the current boundary to catch the best exact solution.

### 6. Small Toy Example

Suppose the [primes](https://ourbigbook.com/codex/prime) were just $\{2,3,5,7\}$, split as $\{2,3\}$ and $\{5,7\}$. The left subsets give log-values for $1,2,3,6$; the right subsets give log-values for $1,5,7,35$.

We then look for the best pair whose combined log does not exceed half of $\log(2\cdot3\cdot5\cdot7)$. The real problem behaves the same way, just on a much larger [prime](https://ourbigbook.com/codex/prime) [set](https://ourbigbook.com/codex/set).

In this toy instance

$$P=2\cdot3\cdot5\cdot7=210,\qquad \sqrt P\approx 14.49.$$

The best valid [divisor](https://ourbigbook.com/codex/divisor) is therefore

$$14=2\cdot7,$$

whereas the nearby product $15=3\cdot5$ already fails because $15^2=225>210$. This makes the [optimization](https://ourbigbook.com/codex/optimization) target concrete: we are not looking for the most balanced subset, but for the largest subset product that stays just below the square-root barrier.

### 7. Modular Output

The final pseudo [square root](https://ourbigbook.com/codex/square-root) is enormous, so the program prints

$$d \bmod 10^{16}.$$

The value itself is computed exactly in the internal [big integer](https://ourbigbook.com/codex/big-integer) representation, and only the displayed form is reduced [modulo](https://ourbigbook.com/codex/modulo) $10^{16}$.

## How the Code Works

The program only accepts `--skip-checkpoints`. The function `primes_below(190)` generates the 42 [primes](https://ourbigbook.com/codex/prime) used in the problem. `enumerate_subsets` computes every subset mask together with its log-sum and sorts the results. The key implementation trick is incremental subset construction: for a nonzero mask, the code removes its lowest [set](https://ourbigbook.com/codex/set) [bit](https://ourbigbook.com/codex/bit), reuses the previous mask sum, and adds one [prime](https://ourbigbook.com/codex/prime) log via `__builtin_ctz`.

`solve_for_primes` computes the total log target, splits the [primes](https://ourbigbook.com/codex/prime) into two halves, and searches the best valid pair by combining the sorted lists. A [monotone](https://ourbigbook.com/codex/monotonicity) pointer finds the boundary in the right list, and then only a very small neighborhood around that boundary is rechecked with exact arithmetic. So [logarithms](https://ourbigbook.com/codex/logarithm) guide the search, but exact [integer](https://ourbigbook.com/codex/integer) comparison still decides the winner.

Once a promising pair of masks is found, `build_from_masks` reconstructs the exact product as a `BigInt`. The helper `square_leq` checks whether the square stays below the full product. The `BigInt` type implements fixed-width multiword multiplication and exact division by $10^{16}$ for the final printout.

The checkpoint routine compares the fast solver with a [brute-force search](https://ourbigbook.com/codex/brute-force-search) for smaller [prime](https://ourbigbook.com/codex/prime) limits such as 30, 40, and 50. These checks confirm that the [meet-in-the-middle](https://ourbigbook.com/codex/meet-in-the-middle-algorithm) logic and the exact validation agree with [exhaustive search](https://ourbigbook.com/codex/exhaustive-search) on small instances.

## Complexity Analysis

If there are $n$ [primes](https://ourbigbook.com/codex/prime), each half has about $2^{n/2}$ subsets. Enumeration, sorting, and the guided neighborhood scan dominate the cost, so the runtime is about

$$O(2^{n/2}\log 2^{n/2})$$

and the memory usage is about

$$O(2^{n/2}).$$

For $n=42$, this is feasible, while the naive $2^{42}$ search is not.
