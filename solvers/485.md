# Project Euler 485 Solution - Maximum Number of Divisors

<https://projecteuler.net/problem=485>:

* [485.py](485.py)

## Problem Summary

Let $\tau(n)$ denote the number of positive [divisors](https://ourbigbook.com/codex/divisor) of $n$. For fixed [integers](https://ourbigbook.com/codex/integer) $u$ and $k$, define

$$M_n=\max_{n \le j \le n+k-1}\tau(j),\qquad S(u,k)=\sum_{n=1}^{u-k+1} M_n.$$

So each length-$k$ interval contributes the largest [divisor](https://ourbigbook.com/codex/divisor) count appearing inside that interval, and the task is to add those maxima over all consecutive intervals from $1$ up to $u$. A naive method would recompute each maximum independently and would be far too slow for the full input size, so the solution splits the problem into two linear passes.

## Mathematical Approach

### Step 1: Formula for the Divisor Count

If

$$n=\prod_{r=1}^{t} p_r^{a_r},$$

then every [divisor](https://ourbigbook.com/codex/divisor) of $n$ is obtained by choosing an [exponent](https://ourbigbook.com/codex/exponent) $b_r$ with $0 \le b_r \le a_r$ for each [prime](https://ourbigbook.com/codex/prime) $p_r$. Hence

$$\tau(n)=\prod_{r=1}^{t}(a_r+1).$$

This [multiplicative](https://ourbigbook.com/codex/multiplicative-function) formula is the starting point for the [number-theoretic sieve](https://ourbigbook.com/codex/number-theoretic-sieve). Instead of factoring each [integer](https://ourbigbook.com/codex/integer) from scratch, the implementation builds all values $\tau(1),\tau(2),\dots,\tau(u)$ incrementally.

### Step 2: Linear Sieve Recurrence

Suppose $n=p^a m$ with $p \nmid m$. Then

$$\tau(n)=(a+1)\tau(m).$$

Multiplying by a [prime](https://ourbigbook.com/codex/prime) gives two cases.

$$\tau(np)=
  \begin{cases}
  2\tau(n), & p \nmid n,\\
  \tau(n)\dfrac{a+2}{a+1}, & n=p^a m,\ p \nmid m.
  \end{cases}$$

The first case adds a new [prime factor](https://ourbigbook.com/codex/prime-factor) of [exponent](https://ourbigbook.com/codex/exponent) $1$; the second increases the [exponent](https://ourbigbook.com/codex/exponent) of an existing [prime factor](https://ourbigbook.com/codex/prime-factor) from $a$ to $a+1$. The implementations maintain, for each [integer](https://ourbigbook.com/codex/integer), its [smallest prime factor](https://ourbigbook.com/codex/smallest-prime-factor) and the [exponent](https://ourbigbook.com/codex/exponent) of that [smallest prime factor](https://ourbigbook.com/codex/smallest-prime-factor). That information is exactly what is needed to apply the [recurrence relation](https://ourbigbook.com/codex/recurrence-relation) in constant time when the next [composite number](https://ourbigbook.com/codex/composite-number) is generated.

The [number-theoretic sieve](https://ourbigbook.com/codex/number-theoretic-sieve) is linear because every [composite number](https://ourbigbook.com/codex/composite-number) is produced once, in its canonical decomposition as a previous [integer](https://ourbigbook.com/codex/integer) multiplied by a [prime](https://ourbigbook.com/codex/prime) chosen under the [smallest-prime-factor](https://ourbigbook.com/codex/smallest-prime-factor) rule. As a result, the full divisor-count table up to $u$ is built in $O(u)$ time.

### Step 3: Reformulate the Outer Sum as Sliding-Window Maxima

Once the table $\tau(1),\dots,\tau(u)$ is available, the problem becomes a standard fixed-window maximum problem. While scanning [integers](https://ourbigbook.com/codex/integer) from left to right, it is convenient to index windows by their right endpoint:

$$W_i=[\,i-k+1,\ i\,],\qquad i=k,k+1,\dots,u.$$

The contribution of window $W_i$ is

$$\max_{j \in W_i}\tau(j).$$

This is the same set of windows as in the original definition, only written by ending position instead of starting position.

### Step 4: Monotone Deque Invariant

The key [data structure](https://ourbigbook.com/codex/data-structure) is a [deque](https://ourbigbook.com/codex/double-ended-queue) of candidate indices. It satisfies two [invariants](https://ourbigbook.com/codex/invariant-mathematics) at all times:

1\. indices in the [deque](https://ourbigbook.com/codex/double-ended-queue) are increasing from front to back;

2\. [divisor](https://ourbigbook.com/codex/divisor) counts are [strictly decreasing](https://ourbigbook.com/codex/strictly-decreasing) from front to back.

When a new index $i$ arrives, all trailing indices $q$ with $\tau(q)\le \tau(i)$ are removed before $i$ is appended. Then any front index $q \le i-k$ is removed because it has left the current window.

After these two clean-up steps, the front of the [deque](https://ourbigbook.com/codex/double-ended-queue) is the index of the maximum [divisor](https://ourbigbook.com/codex/divisor) count in the current window, so its $\tau$-value is added to the answer.

### Step 5: Why Removing Dominated Indices Is Correct

Assume $q<i$ and $\tau(q)\le \tau(i)$. From the moment $i$ is inserted onward, any future window that still contains $q$ also contains $i$, because $i$ is newer and therefore expires no earlier than $q$. Since $i$ has [divisor](https://ourbigbook.com/codex/divisor) count at least as large, $q$ can never again be the unique best candidate for a maximum. So deleting $q$ is always safe.

This domination argument is the whole reason the [deque](https://ourbigbook.com/codex/double-ended-queue) stays short and efficient: each index is inserted once, deleted at most once from the back, and deleted at most once from the front.

### Worked Example

For $u=10$ and $k=3$, the [divisor](https://ourbigbook.com/codex/divisor) counts are

$$\tau(1),\tau(2),\dots,\tau(10)=1,2,2,3,2,4,2,4,3,4.$$

The window maxima are therefore

$$2,3,3,4,4,4,4,4,$$

so

$$S(10,3)=2+3+3+4+4+4+4+4=28.$$

The same mechanism scales to the full input because the expensive part is no longer the window search; it is just a single amortized-constant-time [deque](https://ourbigbook.com/codex/double-ended-queue) update per index.

## How the Code Works

The C++, Python, and Java implementations all follow the same two-stage pipeline. First they build the divisor-count table up to $u$ using the [linear sieve](https://ourbigbook.com/codex/linear-sieve) [recurrence relation](https://ourbigbook.com/codex/recurrence-relation) above. Second they scan that table once with a [monotone deque](https://ourbigbook.com/codex/monotonic-queue) and accumulate the maximum value of each length-$k$ window.

The optimized method is validated on a published checkpoint,

$$S(1000,10)=17176,$$

and one implementation also compares a smaller test case against a brute-force window scan to confirm that the optimized and naive methods agree.

## Complexity Analysis

The divisor-count [number-theoretic sieve](https://ourbigbook.com/codex/number-theoretic-sieve) runs in $O(u)$ time. The [deque](https://ourbigbook.com/codex/double-ended-queue) scan is also $O(u)$ because each index enters the [deque](https://ourbigbook.com/codex/double-ended-queue) once and leaves it at most once. Therefore the overall running time is

$$O(u).$$

The memory usage is $O(u)$ for the divisor-count and [number-theoretic sieve](https://ourbigbook.com/codex/number-theoretic-sieve) tables, plus $O(k)$ for the [deque](https://ourbigbook.com/codex/double-ended-queue). The asymptotic memory bound is therefore

$$O(u).$$
